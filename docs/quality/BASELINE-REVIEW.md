## 分级结论

### P0：基线冻结阻断

- 当前自动化范围内没有未关闭的 P0 代码缺陷。
- 各角色人工批准已于 2026-11-04 记录；冻结仍受治理条件阻断：工作树尚未形成干净候选提交，批准尚未绑定最终 SHA。因此基线为 `APPROVED / PENDING CLEAN CANDIDATE COMMIT`，发布门禁保持 `BLOCKED`。

### P1：生产启用前必须处理

- 认证路由保护尚未启用：缺少登录页、登录回跳、全局 `401` 处理和 `401/403` 集成/E2E 证据。
- GPU 页面仍使用本地 fixture，尚未验证真实 API 的 loading、empty、error、分页和排序。
- 正式发布工作流仍是禁用占位；不得把内部基线等同于可发布生产版本。

### P2：基线后优先改进

- 建立主包与页面 chunk 的性能预算，处理 Vite 的 500 KB 警告；当前基线记录约 `648 KB` minified / `207.6 KB` gzip 的主包现状。
- 增加认证 API、auth store、guard 和错误映射的集成测试。
- 评估 `src/api/index.ts` 聚合出口的包体与耦合风险，业务代码优先领域导入。
- 明确 `429` 的 `RATE_LIMIT` 错误类型，避免长期使用 `CONFLICT`。
- 补充人工 WCAG 检查记录，区分自动化 axe 与人工结论。

### P3：治理与可维护性

- 清理 `pr-check.yml` 与 `ci.yml` 的重叠职责。
- `.codex/skills/` 下 10 个文件已完成 LF 归一化；提交时与功能变更分离。
- 在候选提交上补充依赖审计、构建产物大小和报告路径。

### P4：后续优化

- 按真实业务量评估首屏拆包、路由级懒加载和第三方依赖预算。
- 将发布门禁接入 CI，要求干净 SHA、审批 URL、质量报告和回滚演练证据。

## 安全与部署要求

- Session Cookie 必须由后端设置 `HttpOnly`、`Secure`、合适的 `SameSite` 和受限 `Path`；前端不得读取或持久化 token。
- 跨站请求防护、CSRF 策略、CSP、HSTS、反向代理 TLS 和同源策略必须在部署环境中验证并保存证据。
- `401` 清理本地用户缓存并进入登录流程；`403` 进入统一禁止访问页面；不得在页面层复制权限判断。
- 依赖审计应在候选 SHA 上重新执行；不能以旧工作树结果替代。
