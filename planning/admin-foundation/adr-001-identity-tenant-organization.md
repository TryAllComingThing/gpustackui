# ADR-001：身份、租户与组织边界

- 状态：`PROPOSED / ALL PRODUCT DECISIONS CONFIRMED`
- 版本：v0.2
- 日期：2026-11-15
- 负责人：平台架构、后端、安全、运维与前端负责人
- 关联文档：`decision-log.md`、`capability-map.md`、`role-permission-matrix.md`、`organization-api-contract-v0.2.md`、`organization.openapi.yaml`
- 审批说明：产品经理小张已批准 `decision-log.md` 中 `MANUAL-01` 至 `MANUAL-12` 的全部产品结论及工程默认值（证据 `EVID-2026-11-15-PM-01`、`EVID-2026-11-15-PM-02`）。后端真实 OpenAPI、跨角色技术签批和实现验证完成前，不得进入开发。

## 1. 背景与当前事实

计划在当前 Vue 3 + Nuxt UI 管理框架上建设机构、用户、角色、字典、公告和审计日志等基础管理能力。

仓库当前事实：

- 认证使用 HttpOnly Session Cookie；前端不持久化认证 Token。
- 已实现本地登录、退出、当前用户确认、修改密码、`401/403` 和 CSRF 失败关闭。
- `/auth/config` 报告 SAML/OIDC 可用时，登录页可显示 `VITE_SSO_LOGIN_URL` 入口。
- 退出支持经过白名单校验的外部 SSO 退出地址。
- 权限只有 `is_admin`，没有角色、权限目录、数据范围或业务授权模型。
- 尚未定义机构、用户管理、角色、字典、公告和审计 API。
- 本文中的模型、权限码、事件名和接口均为提案，不代表后端已实现。

因此必须先冻结以下边界：

1. 多租户与 `tenant_id` 的作用域。
2. 租户、机构、用户和角色定义之间的关系。
3. IdP、OIDC 中介、身份绑定、JIT 和破窗登录策略。
4. 后端授权、前端可见性和会话撤销之间的责任边界。
5. 审计事件的可靠写入、失败关闭和保留责任。

## 2. 决策

### 2.1 三层边界：认证、业务授权、前端展示

```text
身份平台 / IdP
  = 登录、SSO、MFA、密码策略、账号联邦、身份声明

业务后端 / BFF
  = 会话、业务用户、租户上下文、机构、角色、权限、数据范围、审计

当前 Vue/Nuxt UI 前端
  = 登录入口、会话展示、菜单/按钮可见性、表单和错误状态
```

- 首期必须接入 IdP；存在企业现有 IdP 时优先复用，否则采用工程默认 Keycloak。
- 业务授权由业务后端负责；IdP 组、前端菜单和角色名都不是业务授权事实源。
- 前端不得自行成为权限事实源，也不得用路由守卫替代后端授权。

### 2.2 多租户是硬边界

平台采用多租户模型，`tenant_id` 是以下数据的硬边界：

- 用户业务档案。
- 机构树。
- 角色定义与角色绑定。
- 权限缓存键。
- 公告、字典、审计事件。
- 数据库唯一约束、索引、分区或行级安全策略。
- 对象存储、搜索索引、缓存和异步任务消息。

规则：

- 普通租户 API 的 `tenant_id` 由服务端从已验证会话或受信网关上下文注入，不接受客户端通过请求头、查询参数或请求体任意切换。
- 跨租户操作只能通过独立的平台管理入口和 `platform_all` 能力执行，必须使用独立权限、独立审计和明确交互。
- 所有租户级唯一约束均以前缀 `tenant_id` 开始，例如 `(tenant_id, code_normalized)`。
- 缓存键至少包含 `tenant_id`；禁止以用户 ID、角色 ID 或机构 ID 单独作为跨租户缓存键。
- 平台级与租户级 ID 均对外表现为不透明字符串；前端不得解析、拼接或比较其内部格式。
- 平台管理员跨租户操作只能使用独立 `/platform/*` 能力；不得通过普通请求头、查询参数或请求体切换租户。

### 2.3 租户与机构分离：单根、最大四级

- 租户是安全与数据隔离边界。
- 机构是租户内的组织、部门或团队树，不是独立认证域。
- 每个租户恰好有一个根机构。
- 机构最大深度为 4 级，根机构计为第 1 级。
- 普通机构创建接口必须提供有效父机构，不提供创建第二个根节点的能力。
- 机构移动必须校验目标父节点、循环引用和移动后的整棵子树深度。
- 用户当前仅属于一个机构；`OrganizationMembership` 不设计为多机构关系。
- 角色绑定的数据范围使用 `self / org / org_subtree / all`，但不得反向推导为用户拥有多个机构成员关系。
- 首期机构只支持停用与启用，不提供删除或恢复；用户调岗、机构移动、停用和启用的影响必须在同一事务内完成，并递增受影响用户的权限版本；本 ADR 不定义机构合并能力。

建议核心关系：

```text
Tenant 1 ── 1 Organization(root)
Tenant 1 ── * Organization
User 1 ── 1 Organization(primary)
User * ── * RoleBinding(role, scope)
Role 1 ── * RolePermission
```

### 2.4 身份账号与业务用户分离

区分：

- **身份账号**：由 IdP 或受控本地认证源维护。
- **业务用户**：包含姓名、状态、所属机构、角色绑定等业务属性。
- **外部身份绑定**：关联业务用户与外部身份。
- **角色绑定**：用户在某个数据范围内拥有哪些角色。

外部身份绑定的稳定键为：

```text
tenant_id + issuer + subject_type + subject_value
```

规则：

- 禁止仅按邮箱、用户名、显示名称或手机号自动绑定账号。
- Microsoft Entra ID 使用 `iss + oid` 作为绑定键，并校验 `tid` 与当前租户的受信映射一致。
- 身份声明缺失、签名失败、`issuer/audience` 不匹配或 `tid` 不匹配时必须失败关闭。
- 身份绑定变更必须审计；解除绑定后必须撤销相关服务端 Session。
- 邀请绑定必须由已授权管理员发起，并绑定到明确的业务用户和机构。

### 2.5 OIDC 中介与 IdP 选型状态

首期必须接入 IdP。企业已有 IdP 时优先复用；没有企业现有 IdP 时采用产品已批准的工程默认 Keycloak。具体发行者、回调地址、客户端注册和运维责任仍须由 IT、安全与运维在部署契约中冻结。

无论选择哪种 IdP，首期协议约束为：

- 使用 OIDC Authorization Code + PKCE。
- 回调、授权码交换、Token 校验和声明映射由业务后端/BFF 完成。
- 浏览器不持有长期 ID Token、Access Token 或 Refresh Token。
- 后端严格校验 `state`、`nonce`、issuer、audience、签名算法、回调地址、时钟偏差和会话关联。
- SAML 仅在现有身份体系明确要求时增加，不并行维护多套主认证链路。
- IdP 组到平台角色的映射必须显式、可审计、可撤销，禁止按组织名或邮箱域名形成隐藏例外。

### 2.6 JIT、邀请绑定和破窗登录

- JIT Provisioning 首期关闭，只允许邀请后绑定。
- 若后续启用 JIT，只能创建无管理角色或待审批用户，必须另行确定默认机构、默认角色、审批人和失败关闭行为。
- 允许受控本地管理员破窗登录；网络仅限受控内网且必须 MFA。首期不额外要求凭证库、轮换、告警或独立破窗审计能力。
- 破窗账号不得用于日常业务操作；高风险操作必须审计。
- 本地退出优先撤销服务端 Session；IdP 退出作为补充，不把浏览器跳转成功等同于服务端会话已失效。

### 2.7 RBAC + 数据范围

首期授权模型为 RBAC + 机构数据范围：

```text
User → UserRoleBinding → Role → Permission
                         └→ DataScope
```

- 功能权限回答“是否能执行某个动作”。
- 数据范围回答“能对哪些对象执行该动作”。
- 后端对列表、总数、详情、写操作和有效权限预览独立授权。
- 前端只消费后端确认后的能力或权限码，用于菜单和按钮展示。
- 首期不引入 ABAC/ReBAC 策略语言；复杂关系授权可在边界稳定后单独 ADR。

数据范围类型：

| 范围 | 含义 | 约束 |
|---|---|---|
| `self` | 仅与调用者本人具有明确资源关系的对象 | 关系必须由具体 API 契约定义，不等同于“本人创建” |
| `org` | 指定机构本身 | 仅覆盖该机构，不包含子树 |
| `org_subtree` | 指定机构及全部后代机构 | 包含指定机构本身 |
| `all` | 当前租户全部范围 | 永远不跨租户 |

首期只启用上述四种标准租户数据范围。`custom` 明确延后，不进入首期 Schema、权限矩阵或页面。`platform_all` 不是普通租户数据范围，只能通过独立平台身份、`/platform/*` 入口和平台权限使用。

### 2.8 角色、内置保护与防提权

建议内置角色：

- `platform_admin`
- `org_admin`
- `auditor`
- `read_only`
- `standard_user`

内置角色实例化为租户级模板，自定义角色只属于当前租户；`platform_admin` 是独立平台身份。首期启用 `tenant_admin`，用于当前租户的自助管理和租户级角色管理，不得跨租户操作。

规则：

- 内置角色不可编辑、不可删除；需要调整时复制为可管理的派生角色。
- 管理员不能授予自己或他人超过自身可授予权限包的角色。
- 管理员不能授予超出自身可授权范围的目标范围。
- 不允许直接给用户自由拼接权限字符串；第一期只允许用户 + 角色 + 范围绑定。
- 首期不开放 `custom` 数据范围；只使用 `self / org / org_subtree / all`。自定义角色不得通过自由拼接范围表达式扩大权限。
- 最后一个有效平台管理员或租户管理员保护必须是事务级原子不变量，不得采用“先查询、后修改”。
- 每个启用租户必须至少保留一个有效 `tenant_admin`；租户自助管理入口只面向当前租户。
- 防提权、最后管理员保护和高风险授权必须写入审计。

### 2.9 会话、权限版本与撤销

区分两个独立版本：

- `permissions_version`：用户授权快照版本。角色、角色权限、用户角色绑定、用户机构、机构层级或用户状态发生影响授权的变化时递增。
- `session_version`：用户会话撤销版本。用户停用、身份绑定解除、密码重置、破窗强制退出或安全事件时递增。

规则：

- `permissions_version` 按用户维护，递增与触发它的业务写操作在同一事务内完成。
- 后端每次请求校验当前用户和租户上下文；缓存授权快照时，缓存键必须包含 `tenant_id + user_id + permissions_version`。
- `session_version` 独立维护，服务端 Session 记录必须关联当前版本；版本不匹配时返回 `401`。
- 角色变更、绑定变更、机构移动和用户停用必须在同一事务中失效或提升权限版本。
- 缓存、消息或授权服务不可用时失败关闭，不得使用过期权限继续放行。
- HttpOnly Cookie 使用 `HttpOnly`、`Secure`、合理 `SameSite` 和受控路径；登录后轮换 Session ID，并设置空闲超时和绝对超时。

### 2.10 审计事件与事务性 Outbox

所有高风险写操作从第一个写操作开始使用统一事件 `audit_event_v1`：

```text
event_id
event_type
event_version = 1
occurred_at
tenant_id
actor_type
actor_id
session_id_hash
request_id
action
resource_type
resource_id
result
reason_code
source_ip
user_agent
before_summary
after_summary
sensitive_fields_redacted
```

规则：

- 审计事件追加写，不提供普通业务修改或删除接口。
- 高风险写操作使用“业务事务 + 事务性 Outbox”；Outbox 写入失败则业务事务失败关闭。
- Outbox 投递失败必须可重试、可告警、可观测；重复投递以 `event_id` 幂等。
- 审计事件不得记录密码、Token、Cookie、密钥、完整身份证件或完整敏感个人信息。
- 登录、SSO 绑定、用户、角色、机构、字典、公告和授权拒绝事件必须可追溯。
- 首期审计仅支持持久保存与授权范围内查询；不开放导出、归档或合规删除。主存储容量、完整性保护和失败关闭由安全/运维确认，不得宣称满足尚未定义的合规保留期。
- 高频日志查询后续可使用 OpenSearch、ClickHouse 或同类检索系统，业务数据库不承担无限增长分析。

### 2.11 统一错误语义

| 场景 | HTTP | 语义 |
|---|---:|---|
| 未认证、Session 失效 | `401` | 清理本地会话并回登录 |
| 已认证但缺功能权限 | `403` | 禁止访问，不泄露对象数据 |
| 对象不存在或在数据范围外 | `404` | 对对象端点优先使用，避免枚举 |
| 列表范围内无数据 | `200` | 返回空列表和授权范围内总数 |
| 缺 `If-Match` 等写前置条件 | `428` | 前端补齐版本后重试 |
| 版本过期 | `412` | 提示刷新或重新加载 |
| 业务状态冲突 | `409` | 展示具体冲突，不自动覆盖 |
| 网络、超时或服务异常 | 无可靠 HTTP 结果 | 页面进入不可用/重试状态，不降级放行 |

## 3. 安全不变量

1. 任何租户数据查询必须隐含 `tenant_id` 约束。
2. 任何对象写操作必须同时校验功能权限、目标对象范围、目标角色可授予性和当前版本。
3. 任何角色分配必须通过 `assertCanGrantRole`；任何用户管理必须通过 `assertCanManageUser`；任何机构移动必须通过 `assertCanMoveOrganization`。
4. 任何授权相关写操作必须递增 `permissions_version` 或明确证明不需要递增。
5. 任何 Session 撤销必须递增 `session_version` 并使旧 Session 失败关闭。
6. 任何高风险写操作必须有 `audit_event_v1` 和 Outbox。
7. 前端隐藏按钮不构成授权；API 必须独立拒绝。
8. 任何未知权限码、未知范围、缺失租户上下文或缺失身份声明均失败关闭。

## 4. 备选方案与取舍

### 方案 A：企业现有 IdP + 业务后端 RBAC（优先评估）

- 优点：复用企业身份治理、MFA 和账号生命周期。
- 风险：不同客户 IdP 能力差异需要适配层。

### 方案 B：Keycloak + 业务后端 RBAC（无现有 IdP 时的推荐默认）

- 优点：标准 OIDC/SAML、MFA 和企业运维能力成熟。
- 风险：需要部署、备份、升级、监控和安全基线；身份主数据与业务用户仍需明确责任。

### 方案 C：Ory、Zitadel、Casdoor 或外部授权引擎

- Ory：组件化程度高，集成和运维复杂度较高。
- Zitadel：适合 B2B 多租户身份，但不自动解决业务机构范围。
- Casdoor：集成较快，但必须验证企业级运维和安全要求。
- Casbin/OpenFGA/SpiceDB：适合后续复杂策略或关系授权，不作为简单后台 CRUD 的默认起点。

### 不采纳

- 前端自建 RBAC 事实源。
- 用角色名写死路由或菜单。
- 用菜单是否显示判断授权。
- 把租户、机构、用户和角色塞进单张用户表。
- 在普通租户 API 中接受客户端任意切换 `tenant_id`。
- 以邮箱、用户名或显示名自动绑定外部身份。
- 使用 localStorage 保存长期细粒度权限或 Token。
- 并行运行多套身份主链路。
- 把 IdP 数据库直接作为公告、字典或审计业务数据库。

## 5. 影响

### 正面影响

- 租户、机构、身份、授权和审计边界可被 API、数据库和前端共同引用。
- 降低先做页面后被多租户和组织模型推翻的风险。
- 让权限撤销、最后管理员保护和审计失败关闭成为可实现契约。

### 代价与风险

- 首次实现需要增加租户上下文、权限版本、Session 版本和 Outbox。
- 机构移动会影响角色范围与权限缓存，需要事务与并发测试。
- IdP 产品方向已确认，但具体发行者、回调、声明映射和运维方案仍须技术签批。
- 租户自助管理需要 `/system/*`、`/content/*` 和 `/audit/*` 页面共用当前租户上下文，并增加 `tenant_admin` 最后管理员保护。
- 当前前端 guard 只有 `authenticated/admin/is_admin`；扩展权限码属于 L3 变更，必须单独评审。
- 后端真实 OpenAPI、多租户、安全和审计技术签批完成前，机构 API 仍不可冻结。

## 6. 迁移与实施顺序

1. 取得后端真实 OpenAPI 或等价 Schema，完成机构 API 字段、错误、版本、幂等和审计对齐。
2. 完成安全/后端/运维/前端对本 ADR 的技术签批；产品经理小张已于 2026-11-15 批准全部产品范围。
3. 签收角色权限矩阵 v0.2。
4. 后端以真实 OpenAPI 冻结机构 API 语义，并关闭其与 v0.2 提案的差异。
5. 完成机构垂直切片 HTML 原型。
6. 形成独立 L3 实现任务契约，列明允许修改路径和测试命令。
7. 实现时同步更新 `docs/architecture/AUTH-AND-PERMISSIONS.md`、`docs/architecture/API-CONTRACT.md`、路由、Schema 和测试。
8. 机构垂直切片通过后，再按用户与角色、字典与公告、审计日志顺序推进。

## 7. 人工决策与证据
