# 管理平台基础规划专家评审报告

- 变更 ID：`admin-foundation`
- 评审日期：2026-11-14
- 评审方式：产品/架构、身份安全、授权系统、后端 API、前端/UX/可访问性联合只读评审
- 评审依据：`review-checklist.md` 推荐顺序
- 评审状态：`REVIEWED / NOT APPROVED`
- 开发状态：**不得进入开发，不得冻结机构 API。**

## 1. 专家团总体结论

| 评审阶段 | 是否可以继续下一轮评审 | 是否可以签收/冻结 | 结论 |
|---|---|---|---|
| ADR-001 身份/租户/组织 | 可以继续专项评审 | 否 | 方向正确，但租户、IdP、权限撤销、审计可靠性和成员关系仍有阻塞项 |
| 角色权限矩阵 | 可以进入问题关闭预评审 | 否 | RBAC + 机构范围的总体方向正确，但数据范围和防提权模型还不可执行 |
| 机构 API v0.1 | 可以进入后端联合确认 | 否 | 适合作为确认会议输入，不足以生成 OpenAPI 或前端请求实现 |
| 交互与原型 | 可以进入高保真准备 | 否 | 适合作为高保真任务书，尚未达到高保真签收或生产实现前置评审 |
| 生产实现任务契约 | 否 | 否 | 上游 ADR、权限和 API 阻塞项未关闭 |

**联合判断：**

1. 不应推翻当前方案重新设计。
2. 不应一次性解决所有细节后再评审，而应先关闭 ADR 的硬决策。
3. 机构 API 和机构页面应作为第一个垂直切片，但必须先完成最小契约冻结。
4. 角色、公告和审计不应与机构切片同时阻塞；采用模块级门槛逐项放行。

## 2. 第一阶段：ADR-001 身份、租户与组织

### 2.1 评审结论

ADR 的以下方向可以保留：

- 身份平台、业务后端、前端三层边界。
- 业务后端是授权事实源，前端只展示。
- 身份账号与业务用户分离。
- `issuer + subject` 外部身份绑定。
- 租户与机构分离。
- RBAC + 机构数据范围。
- HttpOnly Cookie 和审计追加写。
- 优先复用企业 IdP；OIDC 优先，SAML 按需。

但当前 **不能从 `PROPOSED` 进入 `ACCEPTED`**。

### 2.2 阻塞项

| ID | 问题 | 关闭条件 |
|---|---|---|
| ADR-B01 | 单租户/多租户仍是假设，未成为签收决策 | 产品/架构书面确认单租户或定义多租户 `tenant_id` 的服务端注入、唯一约束、索引、审计和跨租户禁令 |
| ADR-B02 | IdP 产品、协议、回调归属、退出和账号绑定未冻结 | 确认 IdP；采用后端/BFF 完成 OIDC 回调、Token 交换和声明校验；定义 JIT、绑定、退出与失败关闭 |
| ADR-B03 | 权限撤销只有“及时失效”，没有可验证时延 | 定义 `authz_epoch` 或等价机制、触发清单、缓存范围、下个请求校验及 `401/403` 区分 |
| ADR-B04 | 审计可靠写入和不可篡改边界未冻结 | 冻结审计 Schema v1、事务性 Outbox 或等价机制、审计失败策略、保留和完整性保护 |
| ADR-B05 | 机构成员关系与角色数据范围关系不清楚 | 决定单/多机构；明确主属机构是否授权；明确机构移动/停用/删除时成员和角色绑定处理 |

### 2.3 高风险建议

1. **SSO 应由后端中介。** 浏览器不持有长期 ID/Access/Refresh Token；后端保存 `state`、`nonce`、PKCE verifier 并完成回调。
2. **业务后端是角色事实源。** IdP 组只允许白名单映射到有限角色，禁止自动映射为 `platform_admin`。
3. **JIT 默认最小权限或待审批。** 未绑定用户不应直接获得默认业务角色。
4. **补足 IdP 与本地 Session 分叉策略。** 明确 IdP 停用用户、单点退出、Back-Channel Logout/SLO 后的最大生效时间。
5. **破窗登录必须有安全控制。** 网络限制、MFA、凭证托管、告警、审计、轮换和失效流程至少确认其一。
6. **Cookie/CSRF 需要部署前提。** 先确认同源/跨域，再决定 `SameSite`、Cookie 名称和作用域；SSO 启动、回调和退出都需独立防护。
7. **SAML 不建议进入首期默认范围。** 除非客户明确要求；若支持，必须使用成熟协议库和独立安全验收清单。
8. **审计补充认证和租户上下文。** 建议包含 IdP、`acr/amr`、租户、操作 ID和会话摘要，且 IP/UA 只信任受控代理。

## 3. 第二阶段：角色权限矩阵

### 3.1 评审结论

保留以下原则：

- 功能权限与数据范围分离。
- 列表、总数、详情、写操作和导出独立授权。
- 不把角色名写进路由。
- 数据范围按绑定逐次判断，不做简单最大值合并。
- 权限码由研发维护，管理员只能分配。
- v0.1 不引入复杂 ABAC/ReBAC。

当前版本 **不能进入机构 API 正式冻结评审**。

### 3.2 阻塞项

| ID | 问题 | 建议 |
|---|---|---|
| PERM-B01 | `self` 同时表示本人、本人创建、本人负责；`custom` 只有一个 `scope_id` 却声称支持对象白名单 | v0.1 暂缓 `custom`，或增加独立 `ScopeGrant`；为每类资源定义范围求值器 |
| PERM-B02 | 防提权未覆盖高权限目标用户 | 操作者不得修改/停用/重置/移动拥有更高权限的用户；源范围和目标范围必须双端校验 |
| PERM-B03 | 有效权限和撤销语义不可执行 | 定义用户、角色、绑定、机构均有效；增加 `revoked_at/version`；使用独立 `authz_epoch` |
| PERM-B04 | 多租户未定，绑定模型没有租户硬边界 | 先关闭 ADR-B01；多租户时角色绑定、审计和缓存键都加入租户上下文 |

### 3.3 高优先级问题

1. **权限码重复/缺失。** `iam:user:assign-role` 与 `iam:role:assign` 语义冲突；`enable` 权限缺失。
2. **后台管理与用户端权限混用。** `system:dictionary:read`、`content:announcement:read` 同时供标准用户和后台页面使用，建议拆分管理权限和普通读取权限。
3. **内置角色保护不一致。** 能力地图/ADR 要求所有内置角色受保护，矩阵只明确保护 `platform_admin`。
4. **角色定义全局但 `role:read` 标记 `SCOPE`。** 需明确角色可见性是全局还是单独策略；数据范围只能属于 `UserRoleBinding`。
5. **越权返回不统一。** 矩阵允许空、`403`、`404` 三种结果，建议统一为缺少功能权限 `403`、对象不存在或范围外 `404`、列表返回授权范围交集。

### 3.4 建议新增授权判定矩阵

至少明确：

```text
allow =
  user.active
  && role.enabled
  && binding.active && !binding.revoked && !binding.expired
  && organization.active
  && role_grants(action)
  && resource_in_scope(action, resource, binding.scope)
```

并写明：

- v0.1 不引入 deny。
- 停用、过期、撤销和范围外是硬排除。
- 多绑定按动作/对象逐绑定判断。
- 角色不继承角色，只允许复制。
- 权限撤销返回 `403`；会话撤销返回 `401`。
- 缓存必须有可证明的最大陈旧时间。

## 4. 第三阶段：机构 API v0.1

### 4.1 评审结论

机构契约 **可以进入后端联合确认阶段**，但不能进入契约冻结或实现。

### 4.2 阻塞项

| ID | 问题 | 关闭条件 |
|---|---|---|
| API-B01 | 单/多租户未定，但契约已使用“租户内唯一” | 单租户改为平台内唯一；多租户先定义服务端租户上下文和全链路边界 |
| API-B02 | 数据范围语义与角色矩阵冲突 | `scope_id` 统一为 opaque string；固定 `403/404`；定义 `org/org_subtree/custom` 对读写动作的行为 |
| API-B03 | API 版本前缀和成功响应外壳有歧义 | 明确 OpenAPI server 为非版本化 `/api`、`paths=/organizations`；HTTP body 不套客户端 `Result<T>` |
| API-B04 | 移动、删除和引用完整性不可实现 | 定义锁/事务、数据库约束、引用清单；无法枚举全部引用时首期只停用或归档 |
| API-B05 | 审计仍是建议字段 | 冻结 Schema、可靠写入、失败策略、去重和删除前快照 |
| API-B06 | 当前不是 OpenAPI | 下一版拆分为业务决策文档 + `organization.openapi.yaml` |

### 4.3 高优先级问题

- **条件请求标准未定。** 明确 `ETag`、`If-Match`、缺失前置条件、格式错误、版本冲突使用 `409` 还是 `412`。
- **动作端点响应和幂等未定。** 为创建、移动、启停、删除明确成功码、响应体、重复调用和 `Idempotency-Key`。
- **错误契约不统一。** 统一 HTTP 状态、通用 `ApiErrorCode`、业务 `ORG_*`；处理 `422`、`RATE_LIMIT` 和 `X-Request-Id`。
- **字段语义未闭合。** 明确 `member_count`、`leader_user_id`、`disabled_at`、`type` 和 `code` 规范化。
- **启停权限未定。** 拆分 `enable/disable` 或统一为 `manage-status`，不能让 `disable` 隐式覆盖 `enable`。
- **树截断不可继续加载。** 增加 `has_children`、`truncation_reasons`、`next_cursor` 或节点继续加载模式。
- **移动和删除约束不一致。** 区分任何子节点、活动子节点、成员、活动成员、角色绑定和业务引用。

### 4.4 中优先级建议

- 分页命名 `perPage/totalPage` 明确为兼容例外或改为 `snake_case`。
- PATCH 明确采用 JSON Merge Patch，并定义 nullable 清空语义。
- 请求未知字段拒绝，响应未知字段允许以保持兼容。
- 删除原因优先使用 `reason_code`，自由文本不得进入 URL。
- 补充 `Location`、`ETag`、递归树 Schema 和字段边界。

## 5. 第四阶段：交互与原型

### 5.1 评审结论

当前文档 **可以作为高保真任务书**，但不能签收高保真，更不能作为生产实现前置评审。

### 5.2 阻塞项

| ID | 问题 | 建议 |
|---|---|---|
| UX-B01 | 能力优先级和高保真优先级都叫 P0，模块门槛不清 | 拆为 `CAP-P0/P1` 和 `HF-P0/P1`，按模块分别放行 |
| UX-B02 | 公告状态机和审计详情选型未闭合 | 冻结公告状态转换、权限、API、审计和幂等；审计详情固定为独立页或宽面板 |
| UX-B03 | 可访问性和窄屏只有原则，没有可测试标准 | 补充树 keyboard、权限矩阵可访问名称、焦点恢复、live region、200% 缩放和 320px 重排 |
| UX-B04 | 上游 ADR/权限/API 门槛未通过 | 当前只能做交互方向和高保真准备，不能形成生产实现任务 |

### 5.3 高优先级问题

1. **导航和路由不一致。** 字典归属“平台配置”，路由却仍在 `/system/dictionaries`；建立唯一页面清单。
2. **机构树技术选型未定。** `UDataTable` 不是树表格；建议首版考虑 `UTree + 详情维护区`，拖拽仅增强。
3. **用户 Drawer 保存语义不清。** 明确哪些 Tab 可编辑、哪些只读、是否原子事务、未保存提示和权限摘要。
4. **权限矩阵规模化不足。** 增加搜索、仅看变更、受保护/只读/禁止授予状态、未保存离开保护和窄屏单组编辑。
5. **复用边界过于乐观。** 明确 `REUSE / EXTEND / NEW`：普通列表复用 `DataTablePattern`；空状态扩展 `UDataTable` 或页面编排；机构树优先 `UTree`；权限矩阵和富文本公告使用页面级组合。

### 5.4 中低优先级建议

- 冻结“机构/组织/部门/公司/租户”等术语。
- 高保真交付物附带状态矩阵、组件映射、字段/API 映射、键盘路径、窄屏和验收路径。
- 记录参考软件版本、日期、许可证和采纳/不采纳项。
- 首期离线模式建议“只读、标记数据可能过期、恢复后用户主动刷新”。
- 修正“减少动画偏好吗”等文案，并补充日期时间、数字和状态列格式。

## 6. 跨文档冲突清单

以下问题必须统一，否则会造成前后端和测试口径分裂：

| 冲突 | 当前情况 | 建议 |
|---|---|---|
| API 基础路径 | 客户端默认路径与文档端点前缀存在歧义 | 明确 OpenAPI server/path；代码相对路径不得重复部署前缀 |
| 机构 ID 类型 | 角色矩阵 `scope_id: number`，机构 API 为 opaque string | 全部统一为 opaque string |
| 越权响应 | 矩阵允许 `403/404/空`，机构 API 推荐 `404` | 缺功能权限 `403`；对象范围外 `404`；列表返回交集 |
| 启停权限 | 机构 API 复用 `disable`，矩阵无 `enable` | 拆分 enable/disable 或统一 `manage-status` |
| 内置角色保护 | ADR/能力地图保护所有内置角色，矩阵只保护平台管理员 | 统一所有内置角色不可原地修改 |
| 角色范围 | ADR 为绑定带范围，能力地图有“角色或绑定设置范围” | 明确只有 `UserRoleBinding` 带范围 |
| 公告状态 | 草稿、待发布、计划发布、已发布口径混用 | 冻结状态机和合法转换 |
| 停用冲突 | 能力地图写“有子机构”，API 写“有活动子节点” | 区分任何子节点、活动子节点、成员和活动成员 |
| 管理/用户端权限 | 标准用户和后台页面复用同一读权限码 | 拆分管理权限和普通用户读取权限 |
| 原型优先级 | 公告/审计能力 P1，高保真又 P0 | 使用不同优先级体系并按模块设门槛 |

## 7. 推荐的关闭顺序

### 第 1 轮：ADR 决策会

先只解决五个问题：

1. 单租户还是多租户。
2. IdP 选型和 SSO 协议边界。
3. `authz_epoch`、会话撤销和缓存失效。
4. 审计可靠写入、失败策略和保留。
5. 机构成员关系与角色范围关系。

输出：ADR-001 修订版和书面决策记录。通过后先更新 ADR 状态，不直接进入页面开发。

### 第 2 轮：权限模型修订

1. 删除或改造不可执行的 `custom` 模型。
2. 形成唯一权限目录和角色可授予矩阵。
3. 补齐 `enable/disable`、后台/用户端权限拆分和内置角色保护。
4. 冻结 `403/404`、列表、详情、导出和写操作授权语义。
5. 定义有效权限算法、撤销字段和测试矩阵。

输出：`role-permission-matrix.md` v0.2。

### 第 3 轮：机构 API 联合确认

1. 修正路径、响应外壳、ID 类型和 `scope_id`。
2. 冻结 `ETag/If-Match`、状态码、幂等和错误 Schema。
3. 明确移动事务、删除引用清单、树截断和字段语义。
4. 产出 `organization.openapi.yaml`。
5. 为每个端点补齐请求、响应、Header、权限和审计样例。

输出：机构 API v0.2 + OpenAPI + 契约测试样例。

### 第 4 轮：交互与高保真准备

1. 拆分 CAP/HF 优先级，建立模块级门槛。
2. 建立唯一页面清单，统一导航、路由和权限码。
3. 选择机构树实现路径。
4. 冻结公告状态机和审计详情形态。
5. 增加可测试的无障碍、窄屏和离线验收矩阵。
6. 明确 `REUSE / EXTEND / NEW` 组件结论。

输出：高保真任务书，先只制作机构切片所需场景。

### 第 5 轮：机构垂直切片实现评审

只有以下条件全部满足后才允许创建实现任务：

- ADR-001 已接受。
- 权限目录和机构相关权限码已冻结。
- 机构 API v0.2 和 OpenAPI 已签收。
- 数据范围、错误语义、乐观锁、审计和会话刷新已确认。
- 机构低保真/高保真已评审。
- 实现任务契约已列出允许修改路径、复用依据、测试命令和风险。

## 9. 最终建议

1. **保留当前方案，不重做。** 主要问题是关键决策未闭合和跨文档口径不一致。
2. **先做 ADR 决策会，不做全量补文档。** 否则权限和 API 文档会继续建立在未确认假设上。
3. **机构切片单独放行。** 不要让公告、审计和复杂权限矩阵同时阻塞机构首版。
4. **冻结权限目录和 OpenAPI 后才进入实现。** 页面 fixture 不能替代契约，`is_admin` 不能模拟 RBAC。
5. **高保真优先机构树。** 权限矩阵、公告和审计各自在自己的模块评审前完成，不要求一次全部完成。
